As três linhas do projeto

main: código principal aprovado. feature/*: desenvolvimento isolado. release/*: preparação opcional de uma versão, com congelamento de funcionalidades e foco em correções.

Ideia → feature/* → PR → CI → QA → Beta → aprovação final → main → tag/release

Não confunda branch com pacote instalável. A publicação oficial exige um release preparado e validado.

Como promover uma melhoria isolada

  1. Verificar git status e preservar mudanças locais.
  2. Confirmar que a funcionalidade tem commits próprios, sem dependências ocultas.
  3. Criar PR de uma branch isolada contra a main; se os commits estiverem misturados, criar branch a partir da main e aplicar somente os commits necessários com git cherry-pick.
  4. Revisar diffs e riscos de segurança.
  5. Executar testes automatizados e manuais, preferencialmente em Windows e Linux.
  6. Corrigir bloqueadores e registrar resultados.
  7. Solicitar aprovação do responsável e integrar sem ignorar regras de proteção.
  8. Publicar tag e notas de versão somente após aprovação.
Cherry-pick pode gerar conflitos e não inclui automaticamente dependências de outros commits. Não execute em sua branch principal sem backup e revisão. Não use force-push para resolver problemas de integração.

Como aprovar apenas uma parte do trabalho

Exemplo: a branch experimental contém editor Monaco, revisão por IA e documentação. Se apenas a documentação está pronta, crie uma branch curta baseada na main, copie ou aplique apenas os commits de documentação, execute a CI e abra um PR. A funcionalidade ainda incompleta continua na branch experimental.

Regra: a aprovação é por mudança e versão, não por simpatia ao autor nem por quantidade de trabalho realizado.

Proteções reais no GitHub

A configuração sugerida é Settings → Rules → Rulesets, regra para main, exigir PR, checks CI, revisão por CODEOWNERS, resolução de conversas, bloqueio de exclusão e force-push e restrição de bypass. O nome exato dos controles varia por plano e tipo de repositório.

Importante: um CODEOWNERS com * @WalneyNF não garante sozinho veto pessoal. É necessário conferir permissões de escrita, administradores, bypass e publicação de releases. Sem confirmar essas configurações, não afirme que a main está protegida.

Testes de qualidade e investigação

Executar npm run typecheck, npm test e npm run build na raiz do Habblaud. Os testes de uma funcionalidade podem passar enquanto a suíte geral falha. Registre ambos os resultados.

Alguns testes de sistemas de arquivos e permissões foram concebidos para ambientes POSIX. Em Windows, diferenças de permissões, links simbólicos e comportamento do Git podem causar falhas. Isso é uma hipótese a verificar, não uma justificativa para ignorar falhas. Compare com CI em Linux e reproduza individualmente antes de decidir.

Matriz de decisão de release

CondiçãoDecisão
CI verde e QA aprovadoElegível para revisão final
Falha de segurança ou perda de dadosBloquear release
Falha apenas de ambiente comprovadaRegistrar evidências e mitigação; decisão explícita
Funcionalidade incompletaManter em feature/beta
Falta de autorização finalNão publicar como oficial

Outras ferramentas que profissionalizam o projeto

Recomendações em ordem de prioridade: painel de qualidade por commit; triagem de issues; modelos de ADR (decisões arquiteturais); changelog automatizado; releases com checksums; testes E2E de interface; análise de dependências; secret scanning; matriz de compatibilidade Windows/Linux; ambiente de demonstração com dados fictícios; portal Habblaud Labs com relatórios; onboarding de novos contribuidores; quadro de roadmap; canal de discussão; sala de agentes com permissões e logs auditáveis.

Esses itens são recomendações, não recursos já implementados.
